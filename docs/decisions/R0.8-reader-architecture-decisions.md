# Architectural Decision Record: R0.8 Reader Scope & Architecture Decisions

## Status
**ACCEPTED** — OQ-10, OQ-16, OQ-17, OQ-18, and OQ-19 are binding R0 decisions. **OQ-9 is provisional:** it records the onboarding default required to build R1, and is confirmed by the R1 usability test (its defined stage in PRD §21) before it becomes binding.

## Decisions Overview

This ADR documents the binding architectural decisions for Mereth Reader scope and architecture: OQ-9 (provisional), OQ-10, OQ-16, OQ-17, OQ-18, and OQ-19. OQ-11–15 remain open for R3/R4/R5.

---

### 1. OQ-9 — Library Model: Open-in-Place vs Managed Library
- **Decision (provisional default):** **Open-in-place** is the recommended onboarding default.
- **Both ownership modes are preserved (FR-7.2):** open-in-place *and* managed-library copy both ship in v1. Managed-library copy is offered as an explicit, non-destructive choice at import time; it is neither eliminated nor hidden. The default only chooses which mode is preselected, not which modes exist.
- **Rationale:** User files already live in organized folder hierarchies, and the default should not surprise users by duplicating their files. Mereth Reader indexes metadata, annotations, and FTS text references locally in SQLite (`mereth_reader.db`) without copying source `.pdf` files unless the user explicitly chooses managed-library copy.
- **Consequence:** In the default mode, original source PDF byte contents remain untouched at their original file locations. A managed-library copy, when chosen, is stored under `app-data/documents/` with the original filename and source path preserved as metadata (FR-7.2). A moved in-place file produces a recoverable locate-file flow (FR-7.2).
- **Confirmation:** deferred to the R1 usability test, which verifies the default with real users before it becomes binding.

### 2. OQ-10 — Annotation Scope: Area Capture vs Freehand Ink
- **Decision:** **Area Capture & Text Highlighting (No Freehand Ink in v1)**
- **Rationale:** Document review focuses on exact text selection, verbatim quotes, and rectangular diagram/table snips. Freehand stylus drawing introduces high vector storage overhead and lower value for the v1 reading-and-notes loop.
- **Consequence:** v1 implements precise text highlights/underlines and normalized 0..1 area-rectangle captures. Freehand ink is deferred past v1.

### 3. OQ-16 — OS & Platform Target: Windows 11 x64 Primary
- **Decision:** **Windows 11 x64 Primary Target**
- **Rationale:** The primary user (PRD §3.1) is a single local user — a student, researcher, engineer, writer, or independent learner — reading long or technical PDFs on a desktop. Windows 11 x64 covers the dominant desktop deployment for that user; Windows on ARM is not required at launch. (Earlier wording that invented an "enterprise legal workstation" persona has been removed — no such persona exists in PRD §3.1, and §17.5's "legal corpus" means redistributable, not law-themed.)
- **Consequence:** Tauri 2 build targets x86_64-pc-windows-msvc with an NSIS per-user installer. Windows on ARM is deferred.

### 4. OQ-17 — Printing Support Scope
- **Decision:** **System Webview Print Dialog Fallback**
- **Rationale:** Custom virtual print drivers add kernel/driver complexity for no v1 benefit. Standard printing is delegated to the OS webview print (`window.print()`) or the system PDF viewer.
- **Consequence:** No custom print driver in the Rust layer for v1.

### 5. OQ-18 — Window Architecture: Single Window vs Multi-Window
- **Decision:** **Single Instance Window with Document Tabs**
- **Rationale:** Opening external files via the OS file manager should route to the active instance — focusing the existing window and loading the document in a new tab — rather than spawning a second process.
- **Consequence:** Single-instance enforcement is wired in Rust via `tauri-plugin-single-instance`; `route_launch_args` resolves the target document path and emits it to the frontend on the `launch-route` event.

### 6. OQ-19 — Password-Protected PDF Handling
- **Decision:** **In-Memory Password Challenge**
- **Rationale:** Password-encrypted PDFs display a modal challenge prompt when loaded. Decrypted bytes exist strictly in volatile memory and are never persisted to disk unencrypted.
- **Consequence:** The `password_encrypted` corpus fixture exercises the prompt-on-load path; passwords are never persisted without a separate security decision.
